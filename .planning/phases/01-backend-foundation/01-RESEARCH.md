### Locked Decisions

- **D-01:** "Connect Facebook Page" = manual token paste only. No OAuth redirect. Operator pastes Page access token + Page ID; backend encrypts and stores. Full OAuth deferred to Phase 6.
- **D-02:** On token paste, verify against the Graph API before storing — call `GET /me` (or `/{page_id}`) to confirm validity, fetch page name and `data_access_expiration_time` to store alongside. Reject invalid tokens at entry.

- **D-04:** If a stored token cannot be decrypted (key lost/changed), detect it and surface a "disconnected" state. Do NOT crash the backend at startup over an undecryptable token.
- **D-05:** Health endpoint returns 200 OK + a trivial DB connectivity query. No FB or Ollama checks here.

## Summary

Phase 1 is a pure scaffold phase: the goal is a running Bun+Elysia server on `127.0.0.1:3000` with a fully-migrated SQLite database, an encrypted FB token column, a settings/FB-connect endpoint, and a health endpoint. No user-facing features beyond FB Page connect are shipped here.

The locked stack (Bun 1.3.14, Elysia 1.4.29, Drizzle ORM 0.45.2 on `drizzle-orm/bun-sqlite`, drizzle-kit 0.31.10) is stable and verified against the npm registry as of 2026-06-23. Every component is confirmed installable with no postinstall network scripts. The `bun:sqlite` built-in and `node:crypto` AES-256-GCM are available in Bun 1.3.14 with no additional packages — verified via live runtime test on the target machine.

The most critical ordering concern is that `PRAGMA journal_mode=WAL` and `PRAGMA busy_timeout=5000` must be run at connection open, before any Drizzle operation, because `busy_timeout` is a per-connection setting. WAL mode is persistent in the file header once set (future connections inherit it), but `busy_timeout` resets to 0 on every new connection and must be set on every open. The Phase 1 migration plan must run both pragmas immediately after `new Database(path)`, before calling `migrate()`.

For the Facebook Graph API token verification (D-02), `GET /me?fields=id,name&access_token={token}` is the correct zero-app-secret verification approach. Using `/debug_token` requires an app access token or developer token, which would expose the app secret to the client — not acceptable. `GET /me` with a Page token returns `id` (the page ID) and `name` (the page name) on success or a `{"error": {...}}` body on failure; this is sufficient for D-02 verification.

**Primary recommendation:** Implement in this order: (1) env validation + fail-fast, (2) DB open + PRAGMAs + migrate() + seed, (3) Elysia app creation + CORS, (4) health route, (5) settings/FB-connect routes, (6) setup script. This ordering ensures every downstream dependency is ready before the next layer initialises.

### Pattern 1: DB Connection with PRAGMAs

**What:** Open `bun:sqlite` Database, set WAL + busy_timeout before handing off to Drizzle.
**When to use:** Always, exactly once at app startup.

```typescript
// Source: https://bun.com/docs/guides/ecosystem/drizzle + PRAGMA pitfall research
import { Database } from 'bun:sqlite'
import { drizzle } from 'drizzle-orm/bun-sqlite'
import * as schema from './schema'

const DB_PATH = process.env.DATABASE_URL ?? 'data/affilytics.db'

export function openDatabase() {
  const sqlite = new Database(DB_PATH)
  // busy_timeout is per-connection and resets to 0 on every new Database(); set immediately
  sqlite.exec('PRAGMA journal_mode = WAL')
  sqlite.exec('PRAGMA busy_timeout = 5000')
  return drizzle(sqlite, { schema })
}

export const db = openDatabase()
```

### Pattern 2: Drizzle Schema (SQLite column builders)

**What:** Define all 7 core entities using `drizzle-orm/sqlite-core` column builders.
**When to use:** Schema is defined once in `db/schema.ts`; drizzle-kit generates migration SQL from it.

```typescript
// Source: https://orm.drizzle.team/docs/column-types/sqlite + https://orm.drizzle.team/docs/sql-schema-declaration
import { sqliteTable, text, integer, real } from 'drizzle-orm/sqlite-core'
import { sql } from 'drizzle-orm'

export const products = sqliteTable('products', {
  id: text('id').primaryKey(),                       // UUID string
  platform: text('platform', { enum: ['shopee', 'lazada', 'tiktok'] }).notNull(),
  name: text('name').notNull(),
  price: real('price').notNull(),
  discountPct: real('discount_pct').notNull().default(0),
  rating: real('rating'),
  reviewCount: integer('review_count'),
  salesCount: integer('sales_count'),
  shop: text('shop'),
  productUrl: text('product_url').notNull(),
  capturedAt: integer('captured_at', { mode: 'timestamp' }).notNull()
    .default(sql`(unixepoch())`),
})

// Integer timestamp mode: values are Date objects in JS, stored as Unix seconds in SQLite
// Use sql`(unixepoch())` for SQLite defaults — NOT NOW() (SQLite doesn't have NOW())
```

> Full schema for all 7 entities follows this same pattern. See Architecture section "Entity Shapes" below.

### Pattern 3: Migration on Boot

**What:** Run `migrate()` synchronously before starting Elysia listener.
**When to use:** Always, in `index.ts` boot sequence after DB open, before `.listen()`.

```typescript
// Source: https://bun.com/docs/guides/ecosystem/drizzle + drizzle-orm/bun-sqlite/migrator confirmed in npm exports
import { migrate } from 'drizzle-orm/bun-sqlite/migrator'

// Synchronous — bun-sqlite migrations do NOT return a Promise
migrate(db, { migrationsFolder: './drizzle' })
```

**Important:** bun-sqlite Drizzle migrations are synchronous (unlike pg/mysql). No `await` needed.

### Pattern 4: AES-256-GCM Encrypt/Decrypt

**What:** Field-level encryption for the `accessTokenEnc` column using Node.js built-in `node:crypto`.
**When to use:** `encrypt()` before INSERT; `decrypt()` before using token in Graph API call; `detectDisconnected()` to catch key rotation.

```typescript
// Source: verified live on Bun 1.3.14 (crypto round-trip + wrong-key error detection confirmed)
import { createCipheriv, createDecipheriv, randomBytes } from 'node:crypto'

// Key: 32-byte buffer derived from BUN_ENCRYPTION_KEY hex string (64 hex chars)
const KEY = Buffer.from(process.env.BUN_ENCRYPTION_KEY!, 'hex')

export function encrypt(plaintext: string): string {
  const iv = randomBytes(12)  // 96-bit IV for GCM
  const cipher = createCipheriv('aes-256-gcm', KEY, iv)
  const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()])
  const tag = cipher.getAuthTag()
  // Storage format: base64(iv):base64(authTag):base64(ciphertext)
  return [iv.toString('base64'), tag.toString('base64'), encrypted.toString('base64')].join(':')
}

export function decrypt(stored: string): string | null {
  try {
    const [ivB64, tagB64, encB64] = stored.split(':')
    const iv = Buffer.from(ivB64, 'base64')
    const tag = Buffer.from(tagB64, 'base64')
    const encrypted = Buffer.from(encB64, 'base64')
    const decipher = createDecipheriv('aes-256-gcm', KEY, iv)
    decipher.setAuthTag(tag)
    return Buffer.concat([decipher.update(encrypted), decipher.final()]).toString('utf8')
  } catch {
    // Wrong key, tampered data, or corrupt stored value → return null (disconnected state)
    return null
  }
}
```

**Key format:** `BUN_ENCRYPTION_KEY` is a 64-character hex string representing a 32-byte key. `Buffer.from(hexStr, 'hex')` produces the 32-byte buffer AES-256 requires.

**Disconnected state (D-04):** `decrypt()` returns `null` on any error. Route handlers check for `null` and return `{ fbConnected: false, reason: 'token_unreadable' }` — never crash on startup.

### Pattern 6: Settings POST with TypeBox Validation

**What:** Validate the FB connect payload with Elysia's built-in `t` (TypeBox).
**When to use:** `routes/settings.ts`.

```typescript
// Source: https://elysiajs.com/essential/validation
import { Elysia, t } from 'elysia'

const settingsRoutes = new Elysia({ prefix: '/api/settings' })
  .post('/fb-connect', async ({ body, set }) => {
    const { pageId, accessToken } = body
    // 1. Verify token against Graph API
    const verified = await fbService.verifyToken(accessToken, pageId)
    if (!verified.ok) {
      set.status = 422
      return { error: 'invalid_token', detail: verified.error }
    }
    // 2. Encrypt and store
    const encryptedToken = encrypt(accessToken)
    await db.update(settings).set({
      fbPageId: pageId,
      pageName: verified.pageName,
      accessTokenEnc: encryptedToken,
      dataAccessExpiresAt: verified.dataAccessExpiresAt,
    })
    return { ok: true, pageName: verified.pageName, dataAccessExpiresAt: verified.dataAccessExpiresAt }
  }, {
    body: t.Object({
      pageId: t.String({ minLength: 1 }),
      accessToken: t.String({ minLength: 10 }),
    }),
    response: t.Union([
      t.Object({ ok: t.Literal(true), pageName: t.String(), dataAccessExpiresAt: t.Optional(t.Number()) }),
      t.Object({ error: t.String(), detail: t.Optional(t.String()) }),
    ]),
  })
```

### Pattern 7: Facebook Token Verification (GET /me)

**What:** Verify a pasted Page access token against the Graph API without needing app secret.
**When to use:** `services/fbService.ts`, called from the settings route before storing.

```typescript
// Source: https://developers.facebook.com/docs/graph-api/reference/debug_token/ +
//         official FB Graph API reference (GET /me default fields)
const FB_VERSION = 'v22.0'

interface FbVerifyResult {
  ok: boolean
  pageName?: string
  pageId?: string
  dataAccessExpiresAt?: number  // Unix timestamp from debug_token data_access_expires_at
  error?: string
}

export async function verifyToken(token: string, expectedPageId: string): Promise<FbVerifyResult> {
  try {
    // GET /me with a Page access token returns the Page node (id, name)
    // No app secret required — the token itself is the credential
    const res = await fetch(
      `https://graph.facebook.com/${FB_VERSION}/me?fields=id,name&access_token=${encodeURIComponent(token)}`
    )
    const data = await res.json() as any
    if (data.error) {
      return { ok: false, error: data.error.message }
    }
    if (data.id !== expectedPageId) {
      return { ok: false, error: `Token is for page ${data.id}, expected ${expectedPageId}` }
    }
    // data_access_expires_at is only available via /debug_token (needs app token).
    // For Phase 1 (manual paste), store null; Phase 6 will add the full OAuth flow
    // which provides data_access_expiration_time in the token exchange response.
    return { ok: true, pageName: data.name, pageId: data.id, dataAccessExpiresAt: undefined }
  } catch (err) {
    return { ok: false, error: String(err) }
  }
}
```

**Note on `data_access_expires_at`:** The `GET /me` approach does NOT return `data_access_expiration_time` — that field is only available from `/debug_token` (which requires an app access token, bringing in the app secret). For Phase 1's manual-paste flow, `dataAccessExpiresAt` is stored as `null`. In Phase 6 (full OAuth), the token exchange response from Meta includes this value. The settings UI should note "re-connect to check data access expiry" for Phase 1 tokens.

### Pattern 8: Setup Script (Key Generation)

**What:** Generate a secure 32-byte hex key and write `BUN_ENCRYPTION_KEY=<hex>` to `.env`.
**When to use:** `scripts/setup.ts`, run once before first backend start.

```typescript
// Source: Bun 1.3.14 — Bun.write + node:crypto randomBytes verified live
import { randomBytes } from 'node:crypto'
import { existsSync, readFileSync, appendFileSync, writeFileSync } from 'node:fs'

const ENV_PATH = '.env'
const VAR_NAME = 'BUN_ENCRYPTION_KEY'

if (existsSync(ENV_PATH)) {
  const existing = readFileSync(ENV_PATH, 'utf-8')
  if (existing.includes(VAR_NAME)) {
    console.log(`${VAR_NAME} already set in .env — skipping`)
    process.exit(0)
  }
}

const key = randomBytes(32).toString('hex')  // 64-char hex string
const line = `${VAR_NAME}=${key}\n`

if (existsSync(ENV_PATH)) {
  appendFileSync(ENV_PATH, line)
} else {
  writeFileSync(ENV_PATH, line)
}
console.log(`${VAR_NAME} written to .env`)
console.log('Next: bun run dev')
```

### Anti-Patterns to Avoid

- **`drizzle-kit push` in production:** Silently drops and recreates columns; use `generate` + `migrate` only (D-07).
- **Setting WAL pragma after Drizzle init:** `migrate()` may create tables before WAL is enabled; always run both PRAGMAs on the raw `Database` object before passing to `drizzle()`.
- **`0.0.0.0` binding:** Makes backend reachable from LAN, violating FOUND-03.
- **Returning decrypted token in API response:** The `GET /api/settings` route must never return `accessTokenEnc` in its response — return only `{ fbConnected, pageName, dataAccessExpiresAt }`.
- **Crashing on decrypt failure:** `decrypt()` returns `null` — the route handler must check for null and return disconnected state, not throw (D-04).
- **`await migrate()`:** bun-sqlite migrations are synchronous — adding `await` has no effect but misleads readers about the call type.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| SQL schema migrations | Custom migration runner | `drizzle-kit generate` + `migrate()` | Handles checksums, ordering, idempotency; built for Drizzle schema format |
| AES-GCM encryption | Custom crypto (XOR, base64 only, etc.) | `node:crypto` AES-256-GCM | GCM provides authenticated encryption; hand-rolled crypto misses auth-tag integrity verification |
| Environment variable loading | Custom `.env` parser | Bun native `.env` loading | Bun loads `.env` automatically; no `dotenv` package needed |
| HTTP validation | Manual `if (!body.field)` checks | Elysia TypeBox `t.Object()` | TypeBox provides both runtime validation AND TypeScript type inference from one schema; manual checks duplicate types |
| Token verification | Parse JWT or decode Base64 | `fetch GET /me` on Graph API | Only the Graph API can confirm token is still valid — local parsing can't detect revocation |

**Key insight:** The crypto and migration patterns in this phase look simple but have subtle correctness requirements (IV uniqueness, auth-tag verification, migration ordering). Never substitute a simpler implementation — the pitfalls are invisible until production.

## Common Pitfalls

### Pitfall 1: busy_timeout Silently Resets to 0

**What goes wrong:** `busy_timeout = 5000` is set once at DB init time in a module, but a code path opens a second `Database()` connection (e.g., in a test or a migration script) without setting the pragma. That second connection has `busy_timeout = 0` and fails immediately under write contention.

**Why it happens:** `busy_timeout` is a per-connection setting in SQLite — it resets to 0 on every new `Database()` instantiation. `journal_mode=WAL` is persistent (stored in file header) but `busy_timeout` is not.

**How to avoid:** Always use the shared `db` singleton from `db/client.ts`. Never open a second `new Database()` without also running both PRAGMAs immediately after.

**Warning signs:** `SQLITE_BUSY: database is locked` errors in tests or under concurrent operations.

---

### Pitfall 2: Migration Runs Before WAL PRAGMA

**What goes wrong:** `migrate(db, ...)` is called before `sqlite.exec('PRAGMA journal_mode=WAL')`. The migration creates tables in the default journal mode. A later restart runs the WAL pragma, but the tables were created in rollback journal mode. This is benign on SQLite (WAL mode applies to the whole file after the pragma), but the migration timing is still wrong — all future connections will open in WAL mode due to the file header, but the first run behaves differently.

**Why it happens:** Developers forget that the WAL pragma must be set on the raw `Database` object before passing to `drizzle()`.

**How to avoid:** The correct order is always: `new Database(path)` → `sqlite.exec('PRAGMA journal_mode=WAL')` → `sqlite.exec('PRAGMA busy_timeout=5000')` → `drizzle(sqlite, { schema })` → `migrate(db, ...)`.

---

### Pitfall 3: Token Returned in API Response

**What goes wrong:** `GET /api/settings` accidentally serialises the `settings` row and includes `accessTokenEnc` in the response JSON. Even encrypted, the ciphertext should not be surfaced.

**Why it happens:** ORM `select()` returns all columns by default; developers forget to exclude sensitive columns.

**How to avoid:** Always use `db.select({ fbConnected: ..., pageName: pages.pageName, ... })` with explicit column selection in the settings GET route. Never `db.select().from(pages)` in a route handler.

---

### Pitfall 4: Elysia Listens on 0.0.0.0 by Default

**What goes wrong:** Developer omits `serve.hostname` in the Elysia constructor. Elysia defaults to `0.0.0.0` (all interfaces). The backend becomes reachable from the local network, violating FOUND-03 and the security constraint.

**Why it happens:** `0.0.0.0` is the Elysia default (as confirmed in official docs); the config property is not obvious.

**How to avoid:** Always explicitly set `serve: { hostname: '127.0.0.1' }`. Verify at startup with a log: `console.log(`Listening on http://${app.server?.hostname}:${app.server?.port}`)`.

---

### Pitfall 5: CORS RegExp for chrome-extension Origins

**What goes wrong:** CORS is configured with a string allowlist but extension origins change their ID between dev and prod loads. The extension's `fetch` from the background service worker is blocked with a CORS error even though the backend is running.

**Why it happens:** Chrome assigns a random extension ID during "Load unpacked" dev installs. Using a hardcoded string `chrome-extension://abc123/...` fails for any other ID.

**How to avoid:** Use `/^chrome-extension:\/\//` as a RegExp in the `cors({ origin: [...] })` array. This allows any extension origin during development. For production, replace with the specific packed extension ID.

---

### Pitfall 6: decrypt() Not Returning null on Wrong Key

**What goes wrong:** `decrypt()` throws an unhandled exception instead of returning `null`. Route handlers that call `decrypt()` without try-catch crash the Elysia process with a 500 error.

**Why it happens:** Node.js `decipher.final()` throws `"Unsupported state or unable to authenticate data"` on auth-tag failure — this is a thrown Error, not a return value.

**How to avoid:** Always wrap the entire decrypt block in try-catch and return `null` on any error. The route handler checks for `null` and returns the disconnected state (D-04). **Verified on Bun 1.3.14:** wrong key causes `decipher.final()` to throw with message `"Unsupported state or unable to authenticate data"`.

---

### Pitfall 7: @elysiajs/swagger Deprecation

**What goes wrong:** The Elysia docs label `@elysiajs/swagger` as deprecated and suggest `@elysia/openapi`. Developer switches to `@elysia/openapi` which was created 2026-04-23 (only ~2 months old, 8K weekly downloads vs 123K for swagger).

**Why it happens:** Docs deprecation notice without corresponding npm deprecation marker leads to premature migration.

**How to avoid:** Keep `@elysiajs/swagger@1.3.1` as locked in the stack. It is NOT npm-deprecated (no `deprecated` field in npm metadata, latest=1.3.1). Use it for Phase 1 dev tooling. Do not migrate to `@elysia/openapi` until it has significantly more adoption and stability.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | No | Single-operator local tool; no user sessions |
| V3 Session Management | No | No sessions |

### Known Threat Patterns for Phase 1 Stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| FB token exposure in API response | Information Disclosure | Never return `accessTokenEnc` column; use explicit column selection in DB queries |
| FB token in logs | Information Disclosure | Redact `accessToken` field before any log statement; never log raw request body on settings route |
| Encrypted token in git | Information Disclosure | SQLite DB file must be in `.gitignore`; `.env` (with key) must be in `.gitignore` |
| Backend reachable from LAN | Elevation of Privilege | `serve.hostname: '127.0.0.1'`; does not bind to 0.0.0.0 |
| Weak encryption key (operator-provided) | Spoofing/Tampering | Setup script generates `randomBytes(32)` — operator never crafts the key manually |
| Key committed to git | Information Disclosure | Setup script writes to `.env` which must be in `.gitignore`; CLAUDE.md and README must document this |
| Replay of stored ciphertext | Tampering | AES-256-GCM auth-tag prevents undetected modification; new IV per encryption prevents replay |
